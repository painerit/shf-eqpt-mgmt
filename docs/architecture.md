# Архитектура

## Общая схема

Приложение построено по MVC с выделенными слоями:

- `app/controllers` — веб-интерфейс, админ-раздел и REST API;
- `app/models` — доменные модели, ассоциации, валидации и scopes;
- `app/policies` — Pundit-политики и scopes доступа;
- `app/queries` — поиск, фильтры и сортировка;
- `app/services` — транзакции, JWT, интеграции и генерация PDF;
- `app/jobs` — фоновые задания Active Job;
- `app/serializers` — JSON-представление для REST API;
- `app/views` — ERB-шаблоны веб-интерфейса.

## Веб-запрос

1. `ApplicationController` загружает пользователя из сессии.
2. `Current` фиксирует пользователя, IP и User-Agent для аудита.
3. Pundit проверяет доступ к действию и ограничивает выборку через `policy_scope`.
4. Контроллер применяет query-объект, сервис или модель.
5. Представление выводит названия справочников, а не числовые ID.

## REST API

- Префикс `/api/v1`.
- JWT подписывается `HS256`, срок жизни 24 часа.
- `Api::V1::BaseController` проверяет `Authorization: Bearer`.
- Для выборок используются те же Pundit scopes, что и в веб-интерфейсе.
- Ошибки возвращаются в едином формате `401/403/404/422`.
- Списки содержат `data` и `meta` с пагинацией.

## Транзакции и блокировки

Завершение поверки выполняется в `Verifications::Complete`:

- транзакция с уровнем `READ COMMITTED`;
- `verification.lock!` — `SELECT ... FOR UPDATE` по строке поверки;
- генерация номеров через `DocumentCounter` с блокировкой строки счётчика;
- обновление дат оборудования;
- перевод пункта графика в `completed`;
- запись аудита в той же транзакции;
- постановка задания на публикацию только после успешного коммита.

Уровень `READ COMMITTED` достаточен для нагрузки 50–300 активных поверок в день:
он исключает грязное чтение, а конфликты по одной строке закрываются
пессимистической блокировкой и unique-индексами.

## Внешняя интеграция

- `Integrations::RegistryClient` — HTTP-клиент на Faraday.
- `Integrations::FakeRegistryClient` — локальный режим без внешнего сервиса.
- `PublishVerificationJob` — повторные попытки при временных ошибках.
- Идемпотентность обеспечивается заголовком `Idempotency-Key`.
- Результат сохраняется в `verifications.external_*`.

## Безопасность

- Пароли хранятся через `has_secure_password` и bcrypt.
- Веб-интерфейс использует сессию, CSRF-защиту и `reset_session` при входе.
- REST API защищён JWT.
- Все действия проходят через Pundit.
- Сильные параметры ограничивают массовое присваивание.
- Секреты не хранятся в Git: `master.key`, `.env`, `.env.production`.
